# Repository README frame

This is the current product/app README frame for **snode.c, mqttsuite, AISuite and CodexUI**. The organization profile remains generated by `tools/snodec_sync profile` from `catalog.yml` (rows) and `profile/template.md` (prose). Edit those two files, never `profile/README.md`. Optional `tier` selects product, learn, install or secondary; `title` and `purpose` supply single-line product display text, and boolean `student` adds a Student projects listing. Product rows require title/purpose and product/app kind; learn titles are optional, and secondary products require `student: true`. Packages and DistributionPackages have a separately approved distribution-hub/maintainer structure, owned by DistributionPackages: shared visual language, not this product/app core. Other repository kinds retain their own cores; forks keep upstream READMEs unchanged.

## Authority and preservation

Identity comes from `catalog.yml`; colors and glyphs come from `brand/tokens.yml` and `brand/glyphs/`. Build behavior stays in each repository's existing manifest and workflows. Retain useful project information, complete first-use examples, safety warnings and material qualifications in the README collection. Build prerequisites and build/install commands belong in the linked source guide, not duplicated README sections. Runnable commands must use the source-defined configuration sections. First-success paths link troubleshooting; user guides expose operational/approval/performance limitations before engineering records. Historical records are labeled, and their process notes never imply current acceptance. Prose and links are not immutable: rewrite the presentation and remove redundant passages and their links when they add no information. Existing banners and figures stay byte-identical. Do not import artwork from SNode.C-Landingpages.

Header chips are presentation assets derived from the authoritative accent pairs and kind glyphs, not new logos. Each scoped repository stores light/dark chips beside its existing media. Both variants have a 240×32 canvas, a 24×24 glyph, a 1.5-unit `currentColor` stroke and the checked text/background pair; readable area/kind text is also their alternative text. Banners are not recolored.

## Frame order

1. `header`: original banner, project title, area/kind chip with light/dark variants.
2. `status`: CI · Release · Packages · License, omitting inapplicable badges. Workflow existence is not a promise of automatic push/PR testing. Packages links the existing signed distribution, not an invented publication count. License appears only for an existing file.
3. Repository-authored pitch and relevant product/consumer relationships; remove redundant links.
4. `menu`: **Start · Install · Build · Use · Configure · Architecture · API · Contribute**; retain only available destinations, using the original repository blue-gray SVG block-button style at a consistent 160×28 size with bold 16 px labels matching GitHub body text, with meaningful link titles and image alternative text. The menu contains only linked buttons: no “Text navigation” dropdown or duplicate plain-link row.
5. Kind core, in the order below; text remains repository-authored.
6. Repository-specific sections: nest integration/first-use extensions under First success where they support that journey; deeper walkthroughs belong in existing authoritative guides, with discoverable README entry links.
7. `ecosystem`: organization and direct project relationships.
8. `footer`: existing licensing and independence statements, maintainer, contributing and security links.

Use paired `<!-- snodec:begin NAME -->` / `<!-- snodec:end NAME -->` markers for the five frame blocks. They reserve ownership boundaries for later sync; **there is currently no cross-repository README sync command or workflow**. Authored content changes through reviewable editorial PRs, not automatic enrollment. Never overwrite unmarked authored content or promote this contract into a second catalog.

- **app:** Quick start · What you see · Install · First run · Configuration · Architecture · Documentation · Platforms · Releases.

Update links when a section moves into a guide; do not retain an empty README build section or misleading anchor merely to preserve its old URL. A `docs/README.md` is the documentation section entry point; its generated `section-pages` block routes to child sections and authoritative guides without duplicating their contents. Do not break links to guides that remain in use. Keep one physical source line per prose paragraph.

Preserve complete first successes in L1. The README collection retains essential information; reducing duplicate authorities takes precedence over preserving wording or section location. No placeholder section, unsupported platform promise, unverified release number or invented maintainer contact may be introduced. Existing repository-specific README policies still apply.

## Common navigation semantics and depth

Labels and order alone are insufficient: each standard menu item must perform the same job across the four READMEs. Root and documentation-section menus share the same normalized destinations. Build enters the authoritative source guide directly; the other overview items enter README sections. The existing API item remains a direct reference-site link and is omitted where no API site exists. Do not turn topic guides into copies of the README or duplicate build/configuration procedures to create matching section names.

| Menu label | Entry | Responsibility |
| --- | --- | --- |
| Start | Quick start | A short project-specific route through Install, Use and Configure; Install delegates to Build when needed, with no repeated route descriptions or procedure. |
| Install | README Install | Choose an available route and link directly to its installation/build guide; source-only projects must not imply binary releases. |
| Build | Source guide | Prerequisites, compilation, build options, verification and installation in one authoritative guide; no README intermediary. |
| Use | First success (product) / First run (app) | Reach a working result, with complete retained examples, expected results and boundaries. |
| Configure | Configuration | Runtime endpoints, persisted settings and access boundaries, not CMake options or a generic architecture dump. |
| Architecture | Architecture | Component responsibilities and ownership at overview depth, then detailed architecture references. |
| API | Existing API site | Generated reference lookup; never invent a site. |
| Contribute | Contributing | Project-specific reporting/contribution guidance and existing community defaults. |

Products keep their mandatory product headings; the app keeps its mandatory app headings. Semantic symmetry does not require renaming every kind-specific heading or imposing identical headings on topic guides. Quick start remains a short route, Install contains installation decisions, Build contains compilation decisions, and Use contains execution; these must not be aliases for the same content. When build or installation instructions move into a guide, move their complete commands, prerequisites and prefix/privilege caveats with them. Update all current links; preserve banners, figures, first-use examples, safety meaning and material qualifications.

## Installation presentation

Install with multiple routes begins with **Choose your route.**; omit that prompt for a single source-only route. Follow it with one horizontal paragraph of linked SVG route buttons and one short explanatory paragraph below—not separate route-description rows, a table, grid, bordered panel or long dash separator. Use the existing secondary-button styling and bold SVG arrow at a consistent 160×28 size for route buttons, with descriptive labels and alternative text that omit the decorative arrow. Buttons wrap naturally only when the viewport requires it; do not force an unbroken row. Quick-start role links retain colons instead of long dash separators. Show only available routes, once each: Signed packages before Build from source for packaged products; Build from source alone for source-only products; Native desktop and Browser frontend for CodexUI’s two source routes. Keep route-specific availability, runtime and dependency qualifications in the explanatory paragraph without repeating ordinary links beside the buttons. State the broad supported environment once under Platforms, and link the current package matrix for distribution releases and architectures. The source button goes directly to the build guide, as does the Build menu button. That guide owns prerequisites, compilation, verification and installation; preserve complete commands and prefix/privilege caveats there. Install remains a concise chooser without a second procedure. Runtime/deployment warnings belong in Configuration and retain their safety meaning. Repository-specific routes differ, but their responsibility and entry depth do not.

## Documentation ownership and return navigation

Configuration is an H2 overview in all four READMEs: endpoints, persisted settings and trust boundaries, then the authoritative runtime guide. Build guides own installation and verification; first-success procedures are never duplicated in those guides. Footer contribution links point to the repository's own Contributing section; shared organization defaults must not describe control-repository operations as product contribution instructions.

Supporting pages enrolled in `navigation/plan.yml` use the generated `page-header` block and `#page-overview` anchor. Section folders use `README.md`. The banner identifies the repository and section; its button row has ↑ parent on the left and Repository/Organization on the right. Organization comes first in the HTML because both right-side buttons use `align="right"`. All navigation buttons are 160 px wide; native phone wrapping is accepted. The Organization label stays Organization. Existing root banners stay unchanged, with a right-aligned Organization button underneath and the stable `#project-overview` anchor. Header and section-list blocks are owned exclusively by `python tools/snodec_sync page-headers`; do not hand-edit them. Asset notes and coding-agent instructions are linked documentation, not presentation pages.

Docs indexes retain the common menu as route maps. Individual L2 guides use the generated page header for return navigation and only relevant local navigation, not another complete README menu or a self-linking Build button. Standard menu targets are available on preview branches; preserve meaningful existing anchors when they still name substantive sections. Do not fabricate compatibility or platform support from version numbers alone.

The generated Repository, Organization and ↑ parent buttons provide return navigation; do not add duplicate Back blocks. User guides and implementation/qualification records occupy separately labelled groups in docs indexes; historical records do not define current product behavior.

## Navigation and tables
